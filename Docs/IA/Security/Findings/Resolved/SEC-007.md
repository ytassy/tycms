# SEC-007 — Verrou Composer désynchronisé, validation du build bloquante

État : corrigé et vérifié localement après autorisation de Yann.
Lots : 02, 14.
Révision : `b51758914201fd9ffc5cdcf3e7ebfa4602351e80`.
Gravité projet : renforcement de la reproductibilité de distribution ; aucun
scénario de compromission ni contournement d'autorisation démontré.
Confiance : forte, validation reproduite et chaîne de build lue.

## Comportement et preuve

Les trois dépendances directes ajoutées sont présentes dans le verrou. En
revanche, l'ajout de `extra.google/apiclient-services` au manifeste n'est pas
reflété dans son `content-hash`. Le calcul officiel de Composer reproduit le
hash du verrou lorsque ce seul champ `extra` est retiré d'une copie en mémoire.
Cela situe la désynchronisation ; aucune version à résoudre n'a été modifiée
pour cette analyse.

`composer --no-plugins --no-scripts validate --no-check-publish` sort avec le
code **2** et signale un verrou non à jour. `build/functions.php`, dans
`compileRelease()`, appelle précisément `composer validate --no-check-publish`
avant l'installation. `buildCommand()` lève une exception sur une sortie non
nulle : l'état actuel ne passe donc pas cette étape de validation du build.
La commande a été reproduite sur copies isolées, pas le build complet.

Preuves : [validation](../../Evidence/LOT-02/ComposerRefresh/composer-validate.txt),
[vérification et calculs](../../Evidence/LOT-02/ComposerRefresh/verification.json),
[empreintes](../../Evidence/LOT-02/ComposerRefresh/sources.json).
Le nouvel audit de sécurité est vide : cela ne prouve pas la synchronisation
du verrou et ne remplace pas `validate`.

## Correction retenue et vérification

Yann a autorisé la resynchronisation du verrou après présentation du constat.
`composer --no-plugins --no-scripts update --lock --no-install --no-progress --minimal-changes`
a réussi dans une copie isolée, sans installation ni exécution du hook.
Le résultat a été appliqué après comparaison : seul le champ `content-hash`
change. Les tableaux des 36 paquets de production et 27 de développement sont
strictement identiques, métadonnées comprises.

La validation sur les fichiers finaux sort avec le code **0**. Les deux
avertissements préexistants (licence absente, double déclaration de larapack/dd)
restent ouverts ; ils ne sont pas la cause du blocage corrigé. L'audit des
mêmes versions ne signale aucun avis ; le rafraîchissement le confirme aussi.
Preuves : [correction](../../Evidence/LOT-02/ComposerRefresh/correction.json),
[validation finale](../../Evidence/LOT-02/ComposerRefresh/composer-validate-after.txt)
et [empreintes finales](../../Evidence/LOT-02/ComposerRefresh/sources-after.json).
Pas de build complet ni de nouveaux tests applicatifs : seule une métadonnée
du verrou a changé. La validation bloquante a été revérifiée directement.

Le hook Google est une tâche de suppression des services non sélectionnés
dans `vendor/google/apiclient-services`. Le build conserve `--no-scripts` et
applique lui-même cette sélection : `pruneGoogleServices()` supprime les
services non retenus puis `composer dump-autoload` régénère l'autoload, sans
exécuter de script Composer. Un nom de service absent ou invalide bloque le
build avant toute suppression. Ce nettoyage borné ne démontre aucune
exposition HTTP des services Google.

## Limites et conditions de réouverture

Le manifeste et le verrou sont synchronisés, sans changement de versions,
et la validation réussit. Réouvrir si une modification du manifeste invalide
à nouveau le verrou. Le nettoyage Google est désormais appliqué par
`pruneGoogleServices()` dans la copie de build, sans activer les scripts
Composer. Cette fiche ne démontre aucune compromission applicative.
