# SEC-011 — Redirection externe depuis une URI interprétée comme référence réseau

État : corrigé et vérifié localement ; exposition initiale au serveur non établie.
Lots : 03, 16. Référence : CWE-601.
Révision du constat initial : `1aff26d92a78bccc5d66b067f13dd7614f58e6bc`.
Gravité : **modérée potentielle** pour une redirection de confiance trompeuse ;
aucune fuite de jeton ou prise de compte démontrée.

## Décision, correction et validation courantes

Yann a autorisé la correction simple de SEC-008, SEC-011 et SEC-012.
Base des correctifs : `50cdf55d5ead8891835996b9824f5f649e7b5cf3`, arbre propre
au départ ; changements non commités, identifiés par les
[empreintes et contrôles](../../Evidence/LOT-03/Fixes/README.md).
La suite ciblée réussit : **167 tests, 515 assertions**, sans SQL ni accès
réseau. Les preuves initiales ci-dessous restent attachées à leur révision ;
elles ne décrivent plus le comportement corrigé.

`RedirectResponse` accepte par défaut les chemins internes commençant par un
seul `/` ; il refuse références réseau, antislashs, espaces bruts et contrôles.
Les chemins et query légitimes sont conservés sans utiliser Host ni déplacer
la réponse dans Core. Le runner revient à `/` si l'URI du formulaire est ambiguë.
Le départ SSO passe par `external()` explicitement ; le WF choisit toujours
le fournisseur autorisé, puis la réponse contrôle le format HTTPS (HTTP local).

`RedirectResponseTest` couvre les cibles internes/externes et formats interdits.
`HttpSecurityTest` exerce le vrai refus CSRF de récupération : chemin/query
normal conservé ; URI `//offsite.example/...` ou absolue renvoyée vers `/`.

Limites : normalisation globale de l'entrée HTTP et frontière proxy non modifiées
(SEC-010 reste ouverte), aucun essai Apache/navigateur ni fournisseur SSO réel.
L'arrivée d'une URI ambiguë à PHP n'est toujours pas attestée ; son renvoi externe
est désormais bloqué en PHP. Réouvrir si une cible interne peut changer d'origine
ou si un nouveau départ externe utilise une cible non autorisée par son WF.

## Reproduction et cause initiales

`Request::pathFromUri()` (`Request.php:248`) applique `parse_url` à l'URI
reçue. Pour `//offsite.example/forgot-password`, le chemin retenu est
`/forgot-password`. Le routeur résout donc le contrôleur de récupération.
Le [manuel PHP](https://www.php.net/manual/en/function.parse-url.php) distingue
ce type de référence d'un simple chemin ; la valeur brute reste dans `uri`.

Sur un POST avec des champs présents et un faux jeton CSRF, le vrai
`PasswordResetController` refuse l'action. Le runner récupère son erreur
métier, trouve le GET du même chemin puis redirige vers **`request->uri` brut**
(`ApplicationRouteRunner.php:175`). `RedirectResponse` ne borne pas cette
destination à l'origine du site. Le résultat est un 303 avec
`Location: //offsite.example/forgot-password`, interprétable hors du site.

La [sonde](../../Evidence/LOT-03/HttpAuditTest.php)
`testRejectedCsrfCanProduceAnOffsiteRedirectFromADoubleSlashUri` compare ce
cas au chemin normal qui renvoie bien `/forgot-password`.
[Résultat](../../Evidence/LOT-03/probes.json), clé `redirections`.
La session et SQL sont des doublures : aucune récupération ni aucun e-mail
ne sont exécutés. La preuve s'arrête à la Response PHP, sans émission HTTP.

Le serveur peut refuser ou normaliser le chemin avant PHP. La configuration
effective d'Apache/mutualisé n'a pas été contrôlée ; c'est la raison du
classement initial dans UnderReview malgré le résultat local.

## Options examinées initialement

1. **Recommandé :** définir un contrat de cible HTTP entrante, rejeter les URI
   ambiguës et construire les redirections internes depuis un chemin local
   canonique, avec paramètres explicitement conservés. Vérifier les chemins
   relatifs, langues et callbacks avant de modifier les mécanismes communs.
2. Borner d'abord ce renvoi après erreur à un chemin interne validé, et garder
   le rejet des URI ambiguës comme renforcement séparé : périmètre plus réduit.

Faire confirmer sur une instance **locale isolée** choisie avec Yann que le
double slash arrive intact à PHP. Un curl sans suivi automatique des Location
suffit ; aucune requête sur l'installation hébergée n'est autorisée ici.
Le renvoi borné de l'option 2 et le contrat de RedirectResponse sont réalisés.
Aucun risque proxy n'est accepté par cette correction.
