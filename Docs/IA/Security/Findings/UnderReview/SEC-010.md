# SEC-010 — Contexte Host/proxy dépendant d'en-têtes reçus sans contrôle du pair

État : comportement PHP confirmé ; exposition de l'hébergement non vérifiée.
Lots : 03, 07, 16. Observation : OBS-010. Référence : CWE-346.
Révision : `1aff26d92a78bccc5d66b067f13dd7614f58e6bc`.
Gravité : **modérée potentielle**, dépendante de la confiance dans le serveur.

## Chaîne et protections examinées

`WebRequest::isBehindProxy()` (ligne 67) considère la présence d'un en-tête
Forwarded/X-Forwarded-* comme preuve de passage par un proxy. Aucun contrôle
de `REMOTE_ADDR` ni liste de pairs de confiance n'est effectué dans cette
classe. `authorityFromServer()` (ligne 82) préfère alors X-Forwarded-Host ;
proto et port peuvent aussi provenir des en-têtes. La classe documente que le
serveur web doit en garantir la provenance, sans pouvoir l'attester elle-même.

La [sonde proxy](../../Evidence/LOT-03/probes.json) utilise une adresse distante
factice extérieure, Host `site.example.test` et X-Forwarded-Host
`other.example.test` : PHP retient le second hôte et HTTPS. Le vrai
`SpaceHelper::getSpacesMatchingRequestHost()` sélectionne ensuite un Space
factice de cet autre hôte. Aucune lecture de ressource ou escalade ACL n'est
prouvée : le changement de contexte ne remplace pas les autorisations métier.

Les liens d'e-mail viennent du `main_host` configuré et validé dans MailHelper,
pas directement du Host reçu. GoogleOidc/GenericOAuth choisissent les URI de
retour dans une liste configurée ; la sonde ne démontre donc ni empoisonnement
de récupération de compte, ni envoi d'un code OAuth vers un hôte arbitraire.
Les attributs de cookies SQL et l'origine des iframes consomment aussi le
contexte de requête ; leur impact réel reste à vérifier par scénario.

Yann vise le mutualisé et considère ces en-têtes normalement protégés.
Cette hypothèse d'exploitation est conservée ; aucune configuration attestant
suppression/réécriture n'a été fournie. « Mutualisé » ne caractérise pas le
chemin proxy. Pas de scan ni de requête sur l'hébergement.

## Options et conditions de qualification

1. **Recommandé :** rendre la confiance explicite : ignorer les en-têtes
   transférés par défaut, les utiliser seulement depuis un proxy configuré et
   validé. Prévoir le cas du mutualisé où PHP voit un proxy de l'hébergeur.
2. Conserver le contrat serveur : obtenir une preuve du nettoyage et du blocage
   de l'accès direct au backend. Cette solution dépend de chaque hébergeur et
   doit devenir un prérequis de déploiement contrôlable ; elle n'est pas acquise.

Choisir après clarification du besoin multi-hôtes/HTTPS/proxy. Tester un pair
de confiance, un client direct forgé et les URL/cookies/Spaces légitimes.
L'analyse ne modifie ni configuration ni politique de confiance.
