# Notes de la version en préparation

Ce document présente uniquement les changements utiles aux utilisateurs de Tycms.

## Nouveautés

- File de jobs différés : TyCMS exécute désormais en arrière-plan les traitements qui n'ont pas à bloquer une requête. Un second CRON (`/queue-worker`, jeton `job_worker_token`) draine la file ; le trafic du site peut l'épauler sans jamais bloquer une page. Les messages de bienvenue après inscription locale ou SSO passent par cette file ; l'accueil d'un compte créé par un administrateur reste envoyé immédiatement, car il contient le mot de passe initial. Nouvel onglet **Jobs** dans l'écran **Système** pour consulter, relancer, annuler et purger, et onglet **Documentation** décrivant les deux lignes de CRON à installer. Le bilan **Sécurité** signale un worker sans jeton ou inactif alors que des jobs attendent.
- Modèles d’e-mails : l’administration permet de créer des modèles personnalisés par espace, de modifier leurs informations (libellé, description, mise en page, variables) et de les supprimer. Ils sont hérités par les espaces descendants, personnalisables en contenu par langue et utilisables dans les scénarios d’automatisation par leur clé `custom__…`.
- Catalogue d'extensions : une version publiée peut être diffusée en **bêta** ou en **release**. La bêta n'est servie qu'aux installations qui la demandent ; une bêta peut être promue en release, jamais l'inverse. L'administration indique le canal de chaque version. Chaque source de catalogue a son propre **canal demandé** (Release par défaut, ou Bêta) : une source en bêta reçoit aussi les versions d'essai, les autres sources ne les voient pas.
- Serveur MCP : TyCMS expose un point d'entrée `/ai/mcp` (Model Context Protocol) permettant à un agent IA de lire et modifier le site. L'accès s'effectue avec un jeton d'API rattaché à un compte de service ; les actions à effet externe (e-mails, notifications, Google) sont indisponibles par ce canal.
- Comptes de service : nouvel écran réservé au super administrateur pour créer des comptes sans connexion interactive, gérer leurs jetons d'API et les supprimer. Leurs groupes et rôles se gèrent depuis la liste des utilisateurs, qui distingue désormais les types de comptes.
- Menus : un menu défini par l'utilisateur et encore vide peut être supprimé depuis la liste. Le bouton reste désactivé tant qu'une entrée subsiste.
- Pages : l'atelier conserve un historique des états remplacés (20 versions du jour courant, puis 1 version par jour sur 30 jours glissants). Le bouton **Historique** permet de consulter le JSON d'une version et de la charger dans l'éditeur avant de l'enregistrer. Deux actions de scénario, `core::listPageHistory` et `core::readPageVersion`, exposent ces lectures à l'IA.
- Automatisation : les workflows GitHub Actions envoient une notification Telegram, Slack ou Discord selon les secrets configurés : échec et réussite sur les branches de production, échec et résultats des traitements de tickets et d'analyse. Un push sur une branche de développement ne notifie pas.
- Système : l’onglet **Routes** dispose d’un champ de recherche local pour filtrer les routes par nom, chemin, méthode, contrôleur ou paramètre, sans nouvel appel au serveur.
- E-mails : chaque tentative d’envoi est enregistrée dans un journal dédié, avec son statut (`processing`, `done` ou `failed`), le destinataire, l’objet, le contenu et le détail d’une éventuelle erreur. Les mots de passe, jetons de réinitialisation et autres secrets connus sont remplacés par `[SECRET]`. Un nouvel onglet **Mails** dans l’écran **Système**, réservé au super administrateur, affiche la période conservée et permet de purger tout ou partie de l’historique. La conservation est configurable (`mail_log_enabled`, `mail_log_retention_days`) et une purge horaire s’applique automatiquement.

## Changements

- Automatisation : les actions `core::sendMail` et `core::sendMailTemplate` mettent désormais le message en file au lieu de l'envoyer pendant le scénario. Elles rendent vrai dès l'enfilement ; l'envoi réel a lieu au prochain passage du worker de la file. Un échec SMTP apparaît donc dans l'onglet **Jobs** et non dans l'historique du run.
- Automatisation : l'action d'envoi de modèle devient `core::sendMailTemplate(template, to, ?vars)`. Une nouvelle action `core::sendMail(to, subject, htmlBody)` envoie un corps HTML libre après purification avec le profil e-mail du site, dans l'habillage du Space. Les images des médias y reçoivent une URL absolue, comme pour les modèles.
- Automatisation : après une exécution manuelle réussie, une modale d'information confirme le succès et indique que le détail du run est affiché plus bas.
- Configuration : le bootstrap applique désormais `display_errors`, `log_errors` et `error_reporting_level`. Par défaut, les erreurs PHP ne sont plus affichées aux visiteurs, restent écrites dans le journal du serveur et les dépréciations sont ignorées (`E_ALL & ~E_DEPRECATED`). Le développement continue d'afficher toutes les erreurs. Un nouveau contrôle du bilan **Sécurité** signale une configuration risquée, y compris lorsque l'hébergement n'applique pas les valeurs demandées.

## Corrections

- Automatisation : l'action `core::listUsers` accepte à nouveau ses quatre paramètres (`page`, `perPage`, `search`, `type`). Le catalogue du langage utilisait une signature de secours obsolète qui masquait le paramètre `type` ajouté.
